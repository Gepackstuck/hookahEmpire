# Hookah Empire — Инструкции для агента

## 1. Проект

**Hookah Empire** — изометрическая 2D management/simulation игра о том, как открыть кальянную в гараже.

Ключевая фантазия игрока:
> Игрок придумывает миксы, готовит их, наблюдает реакции гостей, зарабатывает репутацию и деньги и постепенно превращает личный гараж в место, куда хочется возвращаться.

Текущий скоуп — **только Garage MVP**. Будущие бизнес-этапы намеренно вне рамок реализации.

## 2. Технический базис

- Движок: Godot 4.7.2 stable.
- Язык: GDScript.
- Платформа разработки: macOS.
- Для MVP предпочтительна 2D/изометрическая подача.
- Избегать сторонних плагинов без явного согласования.
- Предпочитать встроенные системы Godot.

## 3. Источники истины

Перед существенными изменениями читать:

Когда документация и реализация расходятся — не изобретать новое правило молча. Объяснить расхождение и обновить соответствующий документ до широкой реализации.

## 4. Рабочий метод

Для каждой задачи:

1. Определить текущий milestone в `docs/MVP_PLAN.md`.
2. Читать только релевантные секции архитектуры/дизайна, необходимые для задачи.
3. Изучить существующую реализацию перед редактированием.
4. Делать минимально связное изменение, удовлетворяющее задаче.
5. Переиспользовать существующие системы, а не создавать параллельные.
6. Держать игровую логику отдельно от UI-презентации.
7. Держать контент data-driven.
8. Не реализовывать последующие milestones без явного запроса.
9. Сохранять уже работающее поведение.
10. Обновлять `docs/PROGRESS.md` после значимой milestone-работы.

## 5. Правила качества кода

- Использовать типизированный GDScript, где это практично.
- Предпочитать небольшие сфокусированные классы/скрипты.
- Использовать signals для связи между игровыми системами и UI, где уместно.
- Не связывать жёстко core-системы с конкретными scene nodes или именами кнопок.
- Избегать лишнего глобального состояния.
- Не создавать глобальный singleton для каждой системы.
- Выносить балансные значения в data/config-файлы, где практично.
- Использовать стабильные ID для ингредиентов, рецептов, гостей, мебели, диалоговых узлов и сюжетных событий.
- Валидировать внешний/data-driven контент при загрузке и сообщать понятные ошибки.
- Безопасно падать при отсутствии опционального контента.

## 6. Правила скоупа

Garage MVP включает:

- окружение гаража
- движение и взаимодействие игрока
- друзей/гостей
- диалоговую систему
- ингредиенты и создание рецептов
- книгу рецептов
- quick preparation mode
- manual preparation mini-game
- charcoal/heat management
- re-preparation по запросу гостя
- предпочтения гостей
- тренды
- scoring результата кальяна
- деньги и репутацию
- размещение мебели в гараже
- save/load
- main menu, pause и settings
- ~20-минутное интро
- MVP-финал: игрока приглашают начать обслуживать внешних гостей

НЕ реализовывать следующие бизнес-этапы во время разработки MVP.

## 7. Дизайн-приоритеты

При неизбежных компромиссах сохранять приоритеты:

1. Экспериментирование с рецептами и открытие нового.
2. Приготовление кальяна должно ощущаться интерактивным и приятным.
3. Реакции гостей должны делать экспериментирование осмысленным.
4. Игрок должен понимать, почему результат хороший/плохой, без раскрытия всех скрытых чисел.
5. Гараж должен ощущаться как личное место игрока.
6. Management должен оставаться читаемым и не превращаться в таблицу с цифрами.

## 8. Тестирование и верификация

После изменений:

- Проверить parse/script-ошибки.
- Запустить проект в validation-friendly режиме, доступном на локальной машине.
- Запустить существующие тесты проекта.
- Для игровых фич провести минимальный ручной тест, доказывающий работу фичи.
- Не заявлять, что фича проверена, если она только написана, но не выполнена.

Команды проверки и запуска тестов описаны в `docs/DEV_SETUP.md`.

Точный путь к исполняемому файлу Godot зависит от машины. Не хардкодить угаданный macOS-путь в документации проекта. Определять/использовать настроенную команду проекта или документировать локальную команду отдельно.

- был ли обновлён `docs/PROGRESS.md`

Держать отчёты краткими и фактическими.
